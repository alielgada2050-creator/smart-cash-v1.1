# تقرير الفحص الأمني — v1.0

منهجية: مراجعة يدوية للكود (XSS، الهوية، التخزين، سلسلة الإمداد، المنطق المالي) + اختبارات آلية. لم أشغّل `claude-code-security-review` من المستودع الخارجي (مصدر غير موثوق)، وطبّقت منهجيته نفسها يدويًا.

## ثغرات وُجدت وأُصلحت
| الخطورة | المشكلة | الإصلاح |
|---|---|---|
| عالية | حسابات بلا كلمة مرور تقبل كلمة المرور التجريبية المعروفة | في النسخة النهائية لا تُقبل إطلاقًا (`checkPw`) |
| عالية | كلمات المرور SHA-256 واحدة بملح = معرّف المستخدم (قابلة للكسر بسرعة) | PBKDF2-SHA256 بـ 210,000 دورة وملح عشوائي، مقارنة بزمن ثابت، وترقية تلقائية للقديم عند أول دخول |
| عالية | استعادة نسخة احتياطية تستبدل كل المستخدمين بلا فحص صلاحية | تتطلب صلاحية نسخ كامل (أو خطة فردية)، حد حجم 60MB، إزالة مفاتيح `__proto__` |
| متوسطة | لا توجد CSP؛ مكتبات من CDN بلا SRI | CSP صارمة (`script-src 'self'` + Google فقط، `object-src 'none'`)، وتوطين jszip/xlsx/jsQR/hairline محليًا |
| متوسطة | سجل التدقيق قابل للتعديل بصمت وبسقف 500 | سلسلة تجزئة SHA-256 (كل سجل يرتبط بالسابق) + `auditVerify` + سقف 3000 |
| متوسطة | الفواتير المعتمدة قابلة للتعديل بلا أثر | ختم بصمة عند الاعتماد، والتحقق يكشف أي تغيير (`invoiceTampered`) |
| متوسطة | رمز Google لا يُفحص مُصدره | فحص `iss` و`aud` و`exp` و`email_verified` |
| منخفضة | جلسة تبقى مفتوحة | قفل تلقائي بعد 15 دقيقة خمول |

تأكدت من: لا `eval`/`new Function`/`document.write`، وكل بيانات المستخدم داخل `innerHTML` تمر عبر `esc()`، وروابط واتساب ترميزها `encodeURIComponent`، ومخرجات الذكاء الاصطناعي تُهرَّب (اختُبرت بحقن `<script>`).

## التدقيق الإلكتروني للمعاملات
قواعد محلية: تكرار فاتورة، ضريبة ≠ 15%، تجزئة مشتريات، اعتماد ذاتي، قيم شاذة، التقاط ليلي، اعتماد بلا صورة، مبالغ مستديرة، قفزة شهرية. ثم تحليل الذكاء الاصطناعي اختياريًا (docs/AI_SETUP.md) على إجماليات مجهولة.

## حدود لا يمكن إصلاحها بدون خادم (صريحة)
1. أي شخص يملك الجهاز يستطيع تعديل `localStorage` من أدوات المطور؛ السلسلة والأختام **تكشف** العبث ولا **تمنعه**.
2. الصلاحيات (RBAC) تُنفَّذ في المتصفح؛ مستخدم متمكن يستطيع تجاوزها محليًا. الحماية الحقيقية = تنفيذها في API على خادم.
3. التحقق من رمز Google يتم في المتصفح؛ على الخادم يجب التحقق من التوقيع.
4. البيانات غير مشفرة على القرص (localStorage). للحساسية العالية: تشفير بعبارة مرور أو قاعدة بيانات خلفية.
5. لا يوجد حد معدل حقيقي لمحاولات الدخول (قفل بعد 5 محلي فقط).
**المسار المقترح:** Firebase Auth + Firestore Rules أو API (مخطط `db/` جاهز) مع تحقق من الصلاحيات والرموز على الخادم، ثم تسجيل التدقيق هناك (append-only).

## v1.2 — حماية تسجيل الدخول
| الحماية | التفاصيل |
|---|---|
| تباطؤ تصاعدي | بعد 3 محاولات فاشلة يتضاعف الانتظار (2ث، 4ث… حتى 15 دقيقة) لكل معرّف، وبنفس الرد للحسابات غير الموجودة (لا كشف لوجود الحساب)، مع زمن رد ثابت للفشل |
| قفل الحساب | بعد 5 فشل في الشركات والمنشآت يُقفل الحساب ويفتحه المدير؛ الخطة الفردية لا تُقفل نهائيًا (حتى لا يُحبس المالك) |
| التحقق بخطوتين (TOTP) | RFC 6238 مع Google/Microsoft Authenticator وAuthy؛ رمز لا يُعاد استخدامه؛ 5 محاولات ثم تباطؤ؛ 8 رموز استرداد تُخزَّن مجزّأة وتعمل مرة واحدة؛ إعادة تعيين المدير لكلمة المرور تُلغي الخطوتين |
| Google | `nonce` عشوائي لكل محاولة (يمنع إعادة استخدام الرمز)، فحص `iss/aud/exp/email_verified`، وقائمة نطاقات مسموحة اختيارية `allowedDomains` في `config.js`؛ الدخول بـ Google لا يطلب خطوة ثانية لأن Google نفسها تدير التحقق بخطوتين |
| الجلسة | قفل بعد 15 دقيقة خمول، وحد أقصى 12 ساعة مطلقة |
**حدّ صريح:** سرّ TOTP والعدّادات مخزّنة محليًا؛ من يملك الجهاز يستطيع العبث بها. الحماية الكاملة (تحقق الرمز، العدّادات، حدود المعدل) تُنفَّذ على خادم.
